# Система технических требований и прослеживаемость

## 1. Назначение

Файл переводит общую идею MOTO EYE в набор проверяемых требований. Требования разделены на **базовую вычислительную платформу** (проверяемый стенд) и **целевое устройство** (дальнейшая разработка). Это важно: успешная проверка стенда не должна автоматически закрывать требования к продукту.

**Приоритеты:** `P0` — необходимы для следующего этапа; `P1` — важные функциональные возможности; `P2` — исследовательские и дополнительные задачи. **Статусы:** `PASS`, `PARTIAL`, `OPEN`.

## 2. Требования к вычислительному стенду

| ID | Требование | Метод проверки | Свидетельство | Статус |
| --- | --- | --- | --- | --- |
| SYS-001 | SoC загружает ядро и ОС из eMMC | UART, ADB | BOOT0 → U-Boot → Linux → Android | PASS |
| SYS-002 | Параметры памяти идентифицируются | UART | LPDDR4 2048 MB, eMMC 14.6 GiB | PASS |
| SYS-003 | Android сообщает о завершённой загрузке | `getprop sys.boot_completed` | `1` | PASS |
| SYS-004 | Есть независимый от Android канал отладки | UART 115200 | BOOT0 и shell на COM6 | PASS |
| SYS-005 | ОС доступна с ПК через ADB | `adb devices -l` | `device` | PASS |
| SYS-006 | Доступны системные команды диагностики | `id`, `cat /proc/uptime` | root, uptime | PASS |
| SYS-007 | Работает программное формирование изображения | `wm`, `screencap` | 1280×720 PNG | PASS |
| SYS-008 | 24 часа без непредвиденных reset | Длительный контроль | Не проводился | OPEN |
| SYS-009 | Проверены VBUS/DC5V и ограничения источников питания | Схема, мультиметр, осциллограф | Нет полного протокола | OPEN |
| SYS-010 | Есть резервная процедура восстановления и её инвентарь | Версии, SHA-256, тест-процедура | Часть шагов известна, хеш не сохранён | PARTIAL |

## 4. Прослеживаемость

Свидетельства для SYS-001…SYS-007 содержатся в [протоколе испытаний](verification.md). SYS-008…SYS-010 вынесены в [дорожную карту](roadmap.md), план испытаний — в [test-plan.md](test-plan.md). Требования к дисплею и UX раскрыты в [концепции HUD](hud-concept.md). Требования допускается закрывать только с приложением записи фактической проверки.

## 5. Управление изменениями требований

Изменения проводятся через отдельный Git-коммит или Pull Request, где указывается исходная проблема, новое требование, способ испытания и влияние на ранее проверенные пункты. Если меняется аппаратная ревизия либо Android-образ, существующие статусы `PASS` не переносятся автоматически.
