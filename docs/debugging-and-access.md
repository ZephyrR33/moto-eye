# UART, ADB и управление Android без физического экрана

## 1. Диагностический подход

При отсутствии дисплея наиболее надёжным источником информации о старте платформы остаётся UART0. Когда Android запускает отладочный сервис, становится доступен более удобный ADB. Эти интерфейсы не заменяют друг друга: UART нужен прежде запуска Android, ADB — для полнофункционального администрирования после его запуска.

## 2. UART0: получение сообщений

Проверенная конфигурация стенда:

```text
A133_CORE2 V2 44 (UART0_TX) -> RXD CH341A (3.3 V logic)
A133_CORE2 V2 45 (UART0_RX) <- TXD CH341A (3.3 V logic)
A133_CORE2 V2 41 (GND)      -> GND CH341A
CH341A VCC                  -> НЕ ПОДКЛЮЧАТЬ
Serial: 115200 baud / 8 data bits / parity none / 1 stop bit
Host: Windows 11, в последнем сеансе COM6
```

Эта текстовая схема описывает экспериментальное соединение. Для нового монтажа обязательно сверьте распиновку Core2 V2; выбор логического уровня зависит от конкретного адаптера. При появлении `HELLO! BOOT0 is starting!` подтверждён проход от внутреннего загрузчика платы до ПК.

Для непрерывного отслеживания используется:

```powershell
.\scripts\Watch-A133Uart.ps1 -Port COM6
```

Скрипт отображает события BOOT0, этап `sys.boot_completed=1` из журналов init и сохраняет полученные символы в локальный файл, если передан параметр `-LogPath`. При старте наблюдения уже работающей системы первый BOOT0 тоже может означать **перезагрузку**, а не обязательно штатное первичное включение. Оценка зависит от условий теста.

## 3. Двусторонняя консоль

Для интерактивного управления недостаточно только линии передачи от платы. В первоначальных попытках команды отправлялись до появления работающей shell и оставались без ожидаемого ответа. Успешное выполнение стало очевидным после появления приглашения `console:/ $` и вывода маркеров `===DIAG===`/`===END===`.

Пример безопасной команды, выполняемой **внутри UART shell**, а не в PowerShell:

```sh
echo START_CHECK
getprop sys.boot_completed
getprop init.svc.adbd
cat /proc/uptime
echo END_CHECK
```

Если обмен ведётся через PowerShell `System.IO.Ports.SerialPort`, нужно отключать DTR/RTS, выставлять 115200 и закрывать порт в `finally`. Наличие консоли под root не устраняет необходимости осторожности: через неё доступны системные файлы и команды, способные нарушить загрузку.

## 4. Проверка Android ADB

Windows Platform-Tools доступны по пути, аналогичному:

```powershell
$adb = "$env:USERPROFILE\AndroidTools\platform-tools\adb.exe"
& $adb devices -l
& $adb shell getprop sys.boot_completed
& $adb shell getprop ro.build.version.release
& $adb shell id
```

На момент последней успешной проверки результат `adb devices -l` содержал `device product:ceres_c3 model:QUAD_CORE_A133_c3 device:ceres-c3`. Команда `id` вывела `uid=0(root)` и контекст SELinux `u:r:su:s0`; Android — версия 10. Для дальнейших работ рекомендуется применять [скрипт сводного статуса](../scripts/Get-A133Status.ps1), не встраивая номер конкретного устройства в исходный код.

**При сообщении `unauthorized`** не пытайтесь обходить механизм авторизации без понимания конфигурации текущей прошивки. **При пустом списке** проверяйте USB-соединение, режим gadget, драйвер и системный журнал, а не перезаписывайте прошивку без диагностики.

## 5. Работа с экраном без монитора

Выполненные проверки:

```powershell
& $adb shell wm size
& $adb shell wm density
& $adb shell dumpsys SurfaceFlinger
```

Ответы: `Physical size: 1280x720` и `Physical density: 200`. В SurfaceFlinger присутствует `Display 0 (HWC display 0)`.

Для Windows PowerShell 5.1 надёжнее создавать PNG на Android и затем скачивать его через `adb pull`:

```powershell
& $adb shell screencap -p /sdcard/moto-eye-screen.png
& $adb pull /sdcard/moto-eye-screen.png .\moto-eye-screen.png
```

Не используйте прямое перенаправление бинарного `exec-out screencap -p` в файл через оператор `>` в Windows PowerShell 5.1: текстовая обработка может повредить байты PNG. В репозитории включён скрипт, который применяет перенос через `adb pull`.

Для интерактивного управления экраном можно использовать официальный проект [scrcpy](https://github.com/Genymobile/scrcpy) после проверки совместимости с данной прошивкой. На дату подготовки отчёта запуск scrcpy на A133 **не подтверждён**; это предложенный следующий шаг, а не выполненное испытание.

## 6. Диагностические методы после запуска ADB

```powershell
# Базовые признаки жизни
& $adb shell cat /proc/uptime
& $adb shell getprop sys.boot.completed
& $adb shell getprop sys.boot_completed

# Вспомогательные сведения
& $adb shell getprop sys.usb.state
& $adb shell getprop init.svc.adbd
& $adb shell pm list packages -3

# Логи, читать только в доверенной лабораторной среде
& $adb shell dmesg
& $adb logcat -d
```

В заметках выше `sys.boot.completed` оставлен как отрицательный пример похожего названия: **проверенный ключ — `sys.boot_completed`**. Не следует строить автоматизацию на непроверенном имени свойства.

Комплект диагностики создаёт скрипт `Export-A133Diagnostics.ps1`, который сохраняет системные сведения **локально**. Перед публикацией следует удалить серийные номера, сведения о сетях, идентификаторы USB и другую чувствительную информацию.

## 7. Типичные диагностические развилки

| Симптом | Возможное объяснение | Проверка |
| --- | --- | --- |
| Нет COM-порта | Режим CH341A или неверный драйвер | Диспетчер устройств, VID/PID, переключатель адаптера |
| COM есть, байтов нет | Неверный TX/RX/GND, отсутствие старта, неверный порт | Наблюдать включение питания, проверить логический уровень |
| Логи есть, команды не работают | RX-провод, неверный момент отправки | Дождаться `console:/ $`, запросить `echo` |
| Windows не видит USB | Соединение, VBUS, USB-режим или драйвер | Отключить питание, сверить схему, проверить PnP |
| `adb devices` пуст | USB gadget не настроен/не определяется | `getprop sys.usb.state`, `init.svc.adbd` через UART |
| Плата циклически перезапускается | Питание, PMU, software reboot, watchdog | UART + измерение питания + boot reason |
| `wm size` есть, экрана нет | Логический дисплей ≠ физическая панель | Проверка интерфейса дисплея, DTS, питания панели |

## 8. Известные ограничения отладочного образа

Отладочная прошивка предоставляет root-права через ADB и разрешительный режим некоторых SELinux-проверок в логах. Это удобно для лаборатории, но недопустимо автоматически переносить на готовое устройство. Отдельно не подтверждены настройка защищённой загрузки, аппаратная защита ключей, актуальность патчей Android, USB authorization и конфигурация сетевого доступа.
